# 回收站随加密快照同步，彻底清除才落墓碑

> 状态（2026-11-10）：accepted。补的是 [ADR 0023](0023-recycle-bin-inside-encrypted-vault.md) 留白的"回收站与同步层的映射"；同时把 [ADR 0018](0018-tombstones-in-sync.md) 的墓碑产生时机收窄，合流规则本身不动。

2026-11-10 决定：云端快照的密文里同步的是**完整的库状态**——`entries` 与 `trash` 都在密文内随快照走；**墓碑（删除集）只在"彻底删除"或"回收站到期清除"时产生**。合流因此对回收站零特殊规则：trash 里的条目就是普通条目状态，三方比较照常进行——移入回收站是改动了它，从回收站恢复也是改动了它，两边对同一条目做了不同处理才成为冲突条目（0009 的规则原样覆盖）。手机端删除与桌面同语义：移入回收站。

选"回收站随密文走"而不是"删除立即落墓碑、回收站仅本地"，是因为后者把"30 天可恢复"降级成设备本地承诺：A 删除的条目在 B 上直接消失，B 连后悔的机会都没有；而"拉到墓碑就塞进本地回收站"会造出各设备 trash 互不一致、合流必须对 trash 特判"不算分叉"的特殊规则，复杂度更高且容易写错。与 ADR 0017 的张力要如实记账：云端因此**短暂持有已删条目的密文至多 30 天**（到期清除后才真正从云端消失）。0017 否决的是无上限、永久的历史版本；回收站是有界暴露，这是 0023 的产品决策带来的最小让步，不是 0017 的翻案。

## 后果

- **云端密文解开的明文形状**：`{ entries, trash }`；墓碑仍是密文外的自有字段（`deleted: [{id, at}]`——UUID 对 provider 不泄内容，0018 原样）。云端小格式解析器（接缝 C）按这个形状写，白名单照旧严格。
- **"删除生效"的传播语义**：A 移入回收站 → 云端快照里该条目位于 trash → B 拉到后它出现在 B 的回收站。B 在 A 彻底删除之前恢复它 → 恢复与删除都算"改过" → 冲突条目交人裁决；A 已彻底删除（墓碑）而 B 恢复 → 删除对修改的冲突，0009 规则第 21 条原样覆盖。
- **体积与上限**：trash 计入 8 MiB 与 10000 条上限（0023 已定），云端同步沿用同一条上限。到期清除仍只发生在载入路径（0023），清除产生的墓碑随该设备下一次推送上云。
- **手机端首版不做回收站界面**：拉到的 trash 只是不渲染；删除（移入回收站）与查看条目照常。恢复与清空回桌面做，列入修订 spec 的"明确不做"。

# 桶的写凭证按设备分发，配对码不承担写权限

> 状态（2026-11-10）：accepted（机制层面）。落的是 `docs/specs/2026-10-01-多设备同步.md` 7.3 悬空的"第二台桌面怎么写"；凭证本身的真实性验证（token 能否按声明工作）归阶段 0 真桶闭环。

2026-11-10 决定：spec 7.3 悬空的写凭证问题落定——**每台桌面在档设置里粘贴自己那把桶级 API token**（R2 形态是 Account API token、Object Read & Write、限定到同步用的那一个桶、设过期日期；若按 0012 的备选换阿里云 OSS / 腾讯 COS，其同类长期凭证按同一规则套用），落盘按档用本档主密码包裹为 `.sync-token.enc`——机制与 `.sync-key.enc` 完全同构（ADR 0011 那套 v1 信封）。同一台机器上多个开启同步的档共用同一把 token、各存一份包裹副本。Worker 的写凭证按 ADR 0025 走 binding 或 Cloudflare secret，独立于桌面。**配对码维持 0014 原样：只含代理地址、对象位置、裸同步密钥，永不携带任何桶凭证。**

理由在 7.3 里已论证过一半：按设备单独吊销（控制台删那台的 token，其余设备不受影响）、配对码的留存渠道不升级成写凭证的留存渠道。被否决的三条：① 配对码携带 AK/SK——微信/备忘录里躺着的码变成一把长期写凭证，且无法按设备吊销，0014 的渠道风险被放大而非缓解；② 全组共用一把 token 落每台设备——吊销一台等于吊销全部，"按设备吊销"的卖点消失，与 0014 的轮换哲学正面冲突；③ 短期 STS 凭证——R2 没有 STS，S3 兼容面也没有，技术不可行，不是取舍。

## 后果

- **档目录从三个同步文件变四个**：`.sync-id`、`.sync-key.enc`、`.sync-state.json` 之外新增 `.sync-token.enc`。spec 7.1 的三条纪律原样套用：是文件不是目录（`profile-store` 的 `isDirectory()` 扫描不会认成档）、不参与存在性哨兵、纯本地版对它完全隐形。spec 故事 31"关掉同步删三个文件"相应改四个。
- **token 是设备级概念、落盘是档级包裹**：界面要讲清"一把 token 服务本机所有开了同步的档"；换 token 即各档重新粘贴。"沿用本机已有 token"的便利入口属界面决策，不是格式决策，实现期再定。
- **吊销与轮换是两个独立动作**：吊销一台桌面 = 控制台删那把 token（断写）；轮换同步密钥 = 0014 那套重写云端 + 重新配对（断读）。界面上不许把两者混成一个按钮，文案也不许混称"撤销设备"。
- **改主密码的重包裹路径变两份**：`.sync-key.enc` 与 `.sync-token.enc` 都要用新口令重包，任一失败整体回滚——0024 之前的"不许半态"纪律同一条，只是清单变长。

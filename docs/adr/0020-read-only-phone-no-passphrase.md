# 手机只读端不设口令门槛，信任边界就是手机锁屏

2026-10-01 定：手机只读页**不要求输入任何口令**——同步密钥存在手机浏览器存储里，打开页面即自动取云端快照并解密展示；**不缓存云端密文**，明文只存在于当前标签页的内存里，关掉即无残留。撤销一台手机的访问，手段是回桌面轮换该档的同步密钥（ADR 0014），不是"从设备列表里删掉它"——本设计没有可信设备名单这回事。

为什么不设口令门槛，两条理由都是硬的：① 手机页由第三方托管的 Worker 提供（ADR 0012），在那上面输入主密码，等于把主密码交给一段可能被人换包的 JS；而主密码不只开这一个档的本地库，它还可能被用户在别处复用——泄露主密码比泄露"云端那一份密文可解"严重一个量级。② 桌面端的密钥包裹走信封 v1 的 scrypt（`server/crypto.ts:7`），手机跑不了（WebCrypto 无 scrypt，且 128 MiB 内存不现实），只能退到 PBKDF2——为一个"看起来更安全"的门槛，先把 KDF 弱化一档，不划算。

否决的另两条：什么都不存、每次重粘配对码（那条含裸密钥的码必然要长期存在某个更不可控的渠道里，比如微信文件传输或备忘录，反而更糟）；缓存云端密文以支持离线查看（密文与解它的密钥同在一个浏览器存储 = 等效于存了一份明文，还把信任边界从"联网时"扩到"断网也能被读"）。

## 后果

- **界面上要如实写出这条边界**：手机页首次配对成功时就得告诉用户"这台手机解锁后，任何人打开这个页面都能看到这个档的全部凭据"，并提供一个"清除本机存储"的按钮。不许把它包装成"端到端加密所以安全"。
- **只读端的档粒度是"一码一档"**：手机上看不到任何未配对档的存在，连名字都没有（ADR 0016）。
- **桌面侧仍然全程要主密码**：本条只放宽手机只读端，不影响本地任何解锁路径。

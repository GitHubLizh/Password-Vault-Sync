# 同步失败不阻塞本地保存，只挂一个持续可见的"待同步"状态

2026-10-01 定：**本地保存永远先成功**，同步是紧随其后的独立动作。推送失败（网络不通、401、412 后合流未完成、超时）不回滚本次修改、不拒绝用户编辑、不在后台无限重试；它把该档标成一个显式状态——"待同步 N 条 · 上次同步于 …"，界面上一直可见，手动「同步」按钮永远可用（ADR 0015 的兜底入口）。

理由是这个产品的次序不能倒：本地库是先有的，服务只监听 `127.0.0.1`，云端只是交换介质（ADR 0008）。如果断网时密码库变得不可用，等于把本地库降级成云端的缓存，那是比"另一台还没更新"严重得多的退化。同时否决"静默忽略"——"我以为另一台已经有了"在密码库里是会死人的误导，而 `server/vault.ts:438` 的 `persist` 是纯本地事务，同步不该混进它的失败路径。

## 后果

- **同步状态是新的界面事实**，必须与现有那条只反映本机多标签页变化的 `remoteChanged` 提示（`src/App.tsx:541`）在文案上分开：一个是"云端有变化/未上传"，一个是"本机别人改过了"。不许合并成一句"检测到新版本"。
- **"待同步"必须足够醒目**，否则它会变成一个新的"我备份过了"的错觉。至少包含：条数、上次成功同步的时间、以及失败原因的可展开说明。
- **锁定/关闭页面时的收尾要有定义**：debounce 窗口里用户直接锁定，是"放弃本次推送并留下待同步状态"还是"阻塞到推完"，本条只定了失败不阻塞保存，这个边界留给 spec 明确。
- **412 不算失败**：`If-Match` 不匹配走的是 ADR 0009 + 0018 的合流路径，合流完成后应继续推送，而不是挂"待同步"了事。

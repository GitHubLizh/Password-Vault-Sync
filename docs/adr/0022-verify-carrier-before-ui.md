# 先做实测骨架，实测不过不上界面

2026-10-01 定：首期的第一个交付物不是界面，而是一个**只针对单个档、不带 UI 的最小闭环脚本**：真实桶上依次完成"推 → 改 → 拉 → 三方合流（含删除集）→ 用旧 ETag 发 `If-Match` 应当 412 → 重新合流后再推应当 200"，同时把手机蜂窝网可达性探针（`scripts/carrier-reachability-probe.html`）跑完。三条外部事实——条件写行为、桶 CORS、国内可达性——任一不通，就按 ADR 0012 换载体重测，损失只在一个脚本上。

为什么把顺序定成"实测先于界面"：上一版多设备方案（坚果云 WebDAV + 条目级合流 + GitHub Pages 移动端）已于 2026-09-30 被整体撤回并删净，直接原因是浏览器直连 WebDAV 实测 401、条件写从无证据，而 spec、ADR、12 张工单和实现都已经写完。这次同样的外部依赖在决策时只拿到了文档级证据，不能再拿一遍同样的代价。

## 后果

- **首个同步包的发布节奏被推后一轮**：ADR 0007 定的 `PasswordVaultSync-win-x64.zip` 改名触发点仍是"同步功能开发完毕、真要发第一个包那天"，本轮不提前改任何名字。
- **骨架阶段允许脏代码但不允许脏结论**：脚本产出的实测记录（请求、响应码、ETag 行为）要落进 spec 的事实章节，成为后续实现与验收的依据；不许只用"能跑"两字概括。
- **桌面测出的连通性不算数**：本机推 GitHub 走 `127.0.0.1:29290` 代理，桌面结果不代表手机网络，可达性必须由用户在手机上亲自跑那一遍。

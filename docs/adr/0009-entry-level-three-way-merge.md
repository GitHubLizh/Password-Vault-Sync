# 分叉按条目级三方合流解决，冲突条目逐条人工裁决

2026-10-01 定：两台设备离线各改各的库后再联网时，**由本机做条目级三方合流**（基准快照 / 本机快照 / 云端快照三份对比）：只有一边改动过的条目自动合并，同一条目被两边都改过的**逐条交用户裁决**，不允许任何一边被静默覆盖。被否决的三个备选：整库级二选一（实现省一半，但选"用本机覆盖"就等于悄悄删掉对方新增的所有条目）、租约单一写者（绕开合流，但对象存储上没有事务，租约过期与写失败的边界全靠猜）、最后写入赢（密码库里不可接受）。

可行的前提是我查过的两点：载体侧 `PutObject` 支持 `If-Match` 比对 ETag，不匹配返回 412（S3 官方文档；R2 扩展文档称与 PutObject 的同名条件头行为一致），所以"我发现的云端版本还活着吗"是有真判据的，不是靠回读 md5 猜；数据侧 `VaultEntry` 自带稳定 `id` 与 `createdAt/updatedAt`、`VaultSnapshot` 带 `revision`（`shared/types.ts:16-26`），合流有锚点，**磁盘信封格式一个字节都不用动**（ADR 0001 的 v1 契约继续成立）。

## 后果

- **合流只能在设备上做**：云端只见密文（ADR 0008），服务端不可能代为合并。
- **每台设备必须持久化基准快照**：即"上次确认一致的那份明文快照 + 它的云端 ETag"。这是一份新的本地状态，它的丢失与损坏路径要单独设计（基准丢了就退化成两边都是"新"的二选一）。
- **前提条件**：同一同步组的各设备必须能用同一个主密码解开云端那份密文——否则无法解密做三方对比。跨设备口令不一致的处理另立决策。
- **本条初稿有个洞，已由 [ADR 0018](0018-tombstones-in-sync.md) 补上**：只比条目集无法表达"删除"——一边删掉的凭据在另一边还活着，合流结果就是它复活。现在的输入是三份快照各自的条目集**加删除集**。
- **手机只读端不参与合流**：它只取云端最新快照，没有写路径，因而不需要基准。

# 同步时机由生命周期驱动：解锁拉、写后推，不开云端定时器

2026-10-01 定：同步点挂在会话生命周期上——**解锁/切档时拉一次；每条保存、改设置、删条目之后 debounce 推一次；界面上常驻一个手动「同步」按钮兜底**。不引入任何面向云端的定时器。

需要澄清一个容易看错的事实：`src/App.tsx:287` 里已经有个每 3 秒的轮询，但它打的是本机 `/api/status`，用途是多标签页防覆盖（配合 `server/vault.ts:497` 的 `REVISION_CONFLICT` 409），与云端无关。已有云轮询是个假前提。

否决的三条：① 云端 30～60 秒轮询全自动——跨设备收敛最快，但给一个"只监听 127.0.0.1、`connect-src 'self'`"（`server/app.ts:41`）的应用开一条全天候外联，失败面（超时、401、离线）也变成全天候；② 只在解锁与锁定各做一次——最保守，但推失败而用户直接关掉页面时，改动可能在本地躺很久；③ 纯手动按钮，连解锁都不自动拉——那"我改了为什么另一台没有"会变成长驻问题。

## 后果

- **CSP 与本机监听都不用放宽**：云端读写由 Node 侧发起（不受浏览器 CSP 约束），手机页由 Worker 同源提供（ADR 0012）。`server/app.ts` 的 `connect-src 'self'` 与 `127.0.0.1` 监听原样保留——这是本条最大的好处。
- **长时间挂着页面不会自动发现对方的改动**：现有那条 `remoteChanged` 提示只反映本机变化，云端分叉要靠下一次拉取或手动同步。界面文案不能把两者混成一句"检测到新版本"。
- **写后推必须有失败处理**：网络失败时改动只在本地，界面要留下"尚未同步"的可见状态，而不是静默成功。debounce 期间锁定/关闭页面的收尾行为要单独设计。

# 同步引入一把独立于主密码的同步密钥，落盘时用本档主密码包裹

2026-10-01 定：云端那份快照用**一把随机生成的同步密钥**加密，与各设备的本地主密码无关；这把密钥在每台设备上**以「本档当前主密码包裹」的形式落盘**——即档目录里再放一个小文件（如 `.sync-key.enc`），内容就是一个现有的 version 1 信封，明文是那 32 字节，口令是本档主密码。于是：改主密码只需重新包裹，不牵动云端任何一份密文；换设备时裸密钥走配对渠道，对方收下后用自己的主密码存成自己那份。

否决的三条路：① 主密码即同步口令（强制全组一致）——改主密码时 `server/vault.ts:403` 会新掷 salt 整封重算，而信封是自描述的（salt 被绑进 AAD，`server/crypto.ts:63-71`），结果是"云端那份只认写它那一刻的口令"，其他设备立刻解不开；此外手机只读端要用户输入**真实主密码**，等于把最核心的秘密交给一个浏览器标签页。② 参与同步的档禁止改主密码——改口令是泄露时的刚需，用同步来削弱安全说不通。③ 一份快照多份封装（每设备一把）——要新增多接收者对象结构，成员变动就得重写全部封装，正面撞上 ADR 0001"不动信封"的结论。

## 后果

- **密钥泄露的爆炸半径要说清楚**：拿到裸同步密钥 = 能解云端快照，但**不能**解任何设备本地的 `vault.pvlt`。反之拿到某个档的主密码不含这把密钥（包裹文件另算）。
- **绝不把同步密钥放进 `vault.pvlt` 的明文里**：`snapshot()` 是白名单重建对象（`server/validation.ts:73` 起），未知顶层字段会被**静默丢弃**。纯本地版和旧绿色包与本项目共用同一块磁盘、同一个文件格式，它们读一次再保存就会把密钥抹掉，导致同步关系无声断裂。
- **档目录里又多一个文件**：与 `.sync-id`（ADR 0010）并列，同样不参与"这棵目录里至少还有一个身份档"的哨兵判据。
- **包裹文件随主密码变更而重写**：`changeMasterPassword` 的成功路径上要顺手重包，失败/中断时不能出现"新口令解不开旧包裹"的半态。

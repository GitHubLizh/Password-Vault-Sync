# 每个身份档对应一个云端对象，同步身份锚在档目录内的 .sync-id

2026-10-01 定：同步的单位是**身份档**，一个档对应云端一个对象；跨设备认定"这是同一个档"的依据是档目录里一个明文小文件 `.sync-id`（默认档在 `<存储目录>/.sync-id`，其他档在 `<存储目录>/<名字>/.sync-id`），云端对象的 key 由它派生，**不由档名派生**。

否决的三个备选：① 从库内容派生标识（如首个信封的 sha256）——零新文件，但从备份恢复、改主密码、删档重建这些在密码库里最常见的动作都会让标识变化，把同一个档认成新档；② 写进 `profiles.json`——直接违反 ADR 0001 的"档案事实源"原则，配置一损坏同步身份就丢失，下一轮合流会认错对象；③ 直接用档名当 key——两台机器各自建过同名档（比如都叫"公司"）就会悄悄共用一个对象并合流成一份，等于把无关的两份凭据并起来。

## 后果

- **多出一类磁盘对象**：`.sync-id` 不是密钥，也不参与加解密；它是标识。启动扫描必须把它与 `vault.pvlt` 区分开，"这棵目录里至少还有一个身份档"的哨兵判据仍以 `vault.pvlt` 为准，不以 `.sync-id` 为准。
- **档名不出本机**：云端 key 里没有人类可读的档名，云盘侧看不到"公司/银行/前女友"这类命名；但它看得到对象**数量**与大小。
- **整栋搬家随目录树迁移**：`/api/storage-location` 复制整棵树时 `.sync-id` 跟着走，同步关系不断；旧目录保留的历史副本里也带着一份 `.sync-id`，这不影响新位置。
- **配对传播靠它**：第二台设备要接上同一个档，必须知道这个 ID（见配对决策），所以 `.sync-id` 一旦丢失等于这个档的同步关系断链——它会退化成"本机有这个档、但不知道对应云端哪个对象"。
- **体积上限沿用现状**：单个对象就是一份信封文件，仍受 `MAX_VAULT_BYTES = 8 MiB`（`server/crypto.ts:6`）约束。

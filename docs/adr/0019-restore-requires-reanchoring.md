# 从备份恢复后强制"重新锚定"，方向由人定，不许静默合流

2026-10-01 定：参与同步的档执行"从加密备份恢复"（`/api/restore/confirm`）后，**必须进入一个同步重新锚定步骤**，二选一：① 以本机刚恢复出来的这份为准，全量替换云端；② 丢弃刚恢复的内容，改为从云端拉最新快照。两个分支都会重写基准快照与云端 ETag。**恢复之后直接进入常规合流是被禁止的路径。**

为什么单独立一条：恢复的语义是"我要回到那个时间点"，它天然是一场大规模改写——旧备份条目比云端"新"（`updatedAt` 更早但内容更全），在 ADR 0009 的条目级合流里会被判成"本机改动"，于是云端真的退回旧状态，还会广播到所有设备，而用户完全看不出自己把别人这几天的改动判了死刑。

不动既有守卫：本地覆盖语义照旧，`tests/api.test.ts:448` 那条"确认恢复必须选中归档快照、不与活跃条目合并"的断言继续成立——本条只在恢复成功之后**追加**一个同步步骤，不放宽恢复本身。

## 后果

- **恢复不再是一个动作，而是两个**：界面文案要写清"恢复后还需要决定云端怎么办"，否则用户以为恢复完就结束了。
- **中途放弃要有定义**：恢复完但用户在锚定步骤里关掉页面，本机已覆盖、云端未动、基准还是旧的——这是一个可观测的不一致态，必须由"下次进入时强制先处理它"兜住，不能留成静默分叉。
- **选①要显式警告"其他设备会被这个版本覆盖"**，并且这是本设计里唯一一处"明知会丢别人改动还允许执行"的路径，只有人工确认能放行。

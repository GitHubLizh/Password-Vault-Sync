# 删除以墓碑（删除集）参与同步，删除遇上修改算冲突条目

2026-10-01 定：同步的数据里除了条目集，还带一份**删除集**（`deleted: [{id, at}]`，即墓碑）。合流的输入因此是"三份快照各自的条目集 + 删除集"，规则：一边删而另一边没改过它 → 确认删除；**一边删而另一边改过它 → 算冲突条目，逐条交用户裁决**（确认删除，还是保留对方的修改）；两边都删 → 删除。云端小格式（ADR 0013）里删除集是它的自有字段，**本地 `vault.pvlt` 的明文结构不变**——删除集只存在于云端快照与本机同步状态里，绝不塞进 `VaultSnapshot`（那会撞上 ADR 0011 记录过的"未知字段被 `snapshot()` 静默丢弃"那条雷，`server/validation.ts:73`）。

不做墓碑的三个后果，按严重程度排：① 删掉的凭据在下一次合流时从别的设备上**复活**——用户会看到"我删了它又回来了"，而复活的是含旧密码的明文条目；② 只能靠"参与同步的档不许删条目"绕开，那等于让同步反向砍掉本地刚需功能；③ 靠整库时间戳定胜负，等于推翻 ADR 0009 回到静默覆盖。

## 后果

- **ADR 0009 的三方合流至此才成立**：0009 原本只写了条目集对比，删除无法表达，本条补上那个洞。
- **墓碑要保留多久需要一条规则**（本条不定数值，留给 spec）：它只用于区分"没建过"和"删掉了"，理论上永久保留最准，但会让云端快照无上限增长。
- **两条设备各自新建的条目不会撞号**：条目 `id` 是 UUIDv4 且有正则校验（`server/validation.ts` 里对 `id` 的 `[a-f0-9]{8}-...-4...` 检查），合流时两边新建的直接并存。**副作用是同一凭据可能被录两遍**，重复检测不属于本条决定，先记为未决项。
- **只读端也看见删除集**：手机页不解释语义，但字段在它下载的密文里；对手机没有行为影响（不能写）。
